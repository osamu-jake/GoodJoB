## この文書の読み方（初めて読む人向け）

このADRは、「実装のどこで、どんな理由で、どちらの作り方を選んだか」を1件ずつ記録したものです。基本的に次の流れで表現されています。

1. **文脈** — なぜこの判断が必要になったか（困っていること）
2. **決定** — 何を選んだか
3. **理由** — なぜそれを選んだか（他の案と比べてどう優れているか）
4. **結果** — この決定によって、次に何をする必要が出てくるか

- ステータスは **保留 / 承認 / 却下 / 置換** の4値。決着したものから順に「承認」へ更新する。
- 実装開始後に判断が覆った場合、該当ADRを「置換」にし、新しい番号で書き直す。**上書きはしない。** 「やらなかったことと、やらない理由を言えるか」が評価対象であるため、履歴そのものが成果物になる。
- レビュー後、`docs/adr/0001-xxx.md` のように1決定1ファイルへ分割してリポジトリに置く想定。

# ADR-0001 投資対効果（ROI）を金額で提示するか

**ステータス：保留** — じゃけさんへ確認中。決着するまで要求定義の第1章は着手しない。

## 文脈

引き継いだ2つの資料で、投資対効果（ROI＝かけたコストに対してどれだけ効果があったかを表す指標）の扱いが正反対になっている。

- 提案仕様書（docx）：初年度ROI 3.8倍／投資額を3.2ヶ月で回収／2,000万円の投資承認、というのが提案の柱
- チーム共有資料（pptx）Slide 19：「効果の金額は、いま出しません」と明言

これは言葉の違いではなく提案全体の骨格の違いであり、どちらを採るかで要求定義（＝何を実現すべきかをまとめる最初の作業）の先頭が変わる。

## 選択肢

**A案：金額を出す**
docxの前提となる数値（探索時間の割合20%、それを30%削減できる見込み、人件費736万円）とその計算根拠を、文書と発表の両方に載せる。「これは仮定の値であり、3ヶ月後に実際の数値へ置き換える」と自分から説明する台本が必須。資料づくりの作業が増える。

**B案：金額を出さない**
代わりに「何を測るかは決めている」ことを実装で証明する必要があり、検索の利用状況を可視化するダッシュボード（部門をまたいで検索した割合／検索してもヒットしなかった件数／過去の訴求文言を参考にした回数、を表示する画面）を、あれば良い（Should）から必須（Must）に格上げする。実装側の作業が増える。

## 決定への影響範囲

| 影響先 | A案 | B案 |
|---|---|---|
| 要求定義の第1章 | ROI達成を最優先の要求とする | 「効果を測れる仕組み」を最優先の要求とする |
| F7〜F9（ダッシュボード機能） | あれば良い | **必須** |
| 発表スライド構成 | パート4に3枚 | パート4を1枚に圧縮、代わりに「何をどう測るか」の説明を追加 |
| 3週間の実装負荷 | 中 | 大 |

## 未決事項

# ADR-0002 「言葉の言い回しが違っても意味が近ければ拾う」検索（ハイブリッド検索）の採用

**ステータス：起票（未承認・次回MTGで承認予定）**

## 文脈

本企画が解こうとしている課題は「部門間の断絶」であり、その正体は「使う言葉が違うために、同じ話をしていても検索でつながらない」という問題である。

- ニーズ側（マーケ・生活者）の表現：「夕方になると前髪がベタッとして束になる」
- シーズ側（研究所）の表現：「皮脂による毛髪の可塑化を抑制する高分子被膜の設計」

同じ現象を指しているが、共通する単語が1つもない。W4で実装済みの検索方式（BM25＝単語が一致した文書を探す、いわゆる「キーワード検索」）は単語の一致に基づくため、この2つは**構造的にマッチしない**。

一方で、固有名詞（「ギャツビー」「ヒアルロン酸Na」など）の検索はキーワード検索が圧倒的に強く、「意味の近さで探す検索」（ベクトル検索＝文章を数値の並びに変換し、その数値の近さで似た文章を探す方式）は成分名を取りこぼしてしまう。

## 決定

キーワード検索（BM25）と意味の近さで探す検索（ベクトル検索）の両方を同時に実行し、結果を1つにまとめる「ハイブリッド検索」を採用する。

## 理由

- 単語が一致しない文書を探すには、意味で照合する手段が**必然的に必要**である。W4で学んだから使うのではなく、この課題を解く手段が他にない。
- どちらか片方だけでは必ず見落としが出る。キーワード検索のみ＝言い回しが違うと弱い、意味検索のみ＝成分名などの固有名詞に弱い。両者の弱点は互いに補い合う関係にある。
- キーワード検索はW4で作った仕組みをそのまま使えるため、新しく作る部分は意味検索側とそれらを統合する部分に限られる。

## 検討した代替案

| 案 | 却下理由 |
|---|---|
| キーワード検索のみ（言い換え辞書で単語をつなぐ） | 辞書を作り続けるコストが無限に膨らむ。新しい言い回しに追いつけない |
| 意味検索のみ | 成分名・ブランド名などの完全一致検索の精度が落ちる。現場で実用に耐えない |
| AI（LLM）に言い換えさせて検索範囲を広げる | 使うたびに料金が発生する。応答が遅くなりデモに向かない。判定をAIに任せている印象を与え、「AIが判断しているのか」という質問（Q8）を誘発する |

## 結果

- 文章を数値に変換する処理（バッチ処理）、結果を1つにまとめるロジック（ADR-0003）、その数値変換に使うAIモデルの選定（ADR-0005）が新たに必要になる。
- 検索方式を切り替えるボタン（キーワード検索のみ／意味検索のみ／両方併用）の実装が必須になる。**この切り替えを目の前で見せられるかどうかがデモの成否そのもの**であるため、必須（Must）扱いとする。

# ADR-0003 2種類の検索結果を1つの順位にまとめる方式（RRF）を採用、調整用の値k=60

**ステータス：起票（未承認・次回MTGで承認予定）**

## 文脈

キーワード検索（BM25）が出すスコアと、意味検索が出すスコア（コサイン類似度＝2つの文章がどれくらい似ているかを-1〜1の数値で表したもの）は**そもそも尺度（単位や範囲）が異なり、直接比較したり足し合わせたりできない**。キーワード検索のスコアは検索対象の文書集合によって変わる基準のない数値であり、意味検索のスコアは-1〜1に収まる決まった範囲の数値である。この2つを統合する方式を決める必要がある。

## 決定

RRF（Reciprocal Rank Fusion＝「順位の逆数を足し合わせる」統合方式）で統合する。調整用の定数 k = 60。

```
score(d) = Σ 1 / (k + rank_i(d))
```

（意味：それぞれの検索方式での「順位」を使い、1位に近いほど大きな値になる数を足し合わせて最終的な順位を決める、という計算式）

各検索方式から上位50件を取得し、RRFで統合した後に上位10件を返す。

## 理由

- この方式は**スコアの数値そのものではなく「何位だったか」という順位だけを使う**ため、単位の異なる2つの検索方式を、面倒な下準備なしに統合できる。数値を揃えるための調整（正規化）が不要で、3週間という短い期間に向いている。
- k=60はこの方式の元になった論文（Cormack et al., 2009）で使われている値であり、実務上のデファクトスタンダード（多くの現場で使われている標準的な値）として広く使われている。自分たちで独自に決めた値だと根拠を問われるが、元の論文にある値であれば説明できる。
- kは「順位の差をどれくらい重視するか」を調整する値で、大きいほど上位と下位の差が緩やかになる。60は「上位の結果を尊重しつつ、片方の検索方式にしか出てこない文書も拾い上げる」というバランスの取れた値として機能する。

## 検討した代替案

| 案 | 却下理由 |
|---|---|
| 2つのスコアを揃えてから足し算する方式（min-max正規化） | 「どちらをどれくらい重視するか」の重みを調整する必要があり、その根拠を説明できない。対象の文書が変わると再調整が必要になる |
| 意味検索の結果を、キーワード検索の基準で並び替える | キーワード検索が0件のときに機能しない。本企画がまさに解決したいのはその場面である |
| より高精度な再採点AIモデル（Cross-Encoder）で並び替える | 計算コストが高く、デモの応答速度に影響する。3週間では検証しきれない |

## 結果

- RRFで出るスコアは順位の逆数を足した値であり、上位でも0.03程度の小さい値にしかならない。**そのままではパーセンテージとして表示できない。** 表示方法はADR-0010で別途決定する。
- 各検索方式から取得する件数（50件）は、この統合方式がうまく機能するための下限として設定した。少なすぎると、片方の検索方式にしか出てこない文書を取りこぼしてしまう。

# ADR-0004 専用のベクトル検索用データベースを使わず、単純な計算＋SQLiteで済ませる

**ステータス：起票（未承認・次回MTGで承認予定）**

## 文脈

「意味の近さで探す検索」を実装するにあたり、専用のベクトル検索用データベース（FAISS、Chroma、pgvector等。文章を数値に変換したもの＝ベクトルを高速に検索するための専門ソフト）を導入するかを決める必要がある。対象となる文書の数はシーズ（研究所側）300〜500件、ニーズ（マーケ側）300〜500件、合計1,000件程度。

## 決定

専用のベクトル検索用データベースは導入しない。文章を変換した数値の並び（埋め込みベクトル）は、これまで使っているSQLite（軽量なデータベース）の`embeddings`テーブルに、そのままバイナリデータ（BLOB）として保存する。検索するときは、保存した全件との近さを、その場でシンプルな計算（内積）で求める。

```sql
CREATE TABLE embeddings (
  doc_id INTEGER PRIMARY KEY REFERENCES documents(id),
  vec    BLOB NOT NULL      -- numpy.tobytes() で格納
);
```

## 理由

- 1,000件 × 384次元（1つの文章を384個の数値で表す）の計算は、通常のパソコンで数ミリ秒で終わる。**専用のデータベースが得意とする「大量データからの高速な近似検索」が必要な規模ではない**。
- 既にSQLiteを採用している（W3で作った資産）ため、データの保存場所が1つで済む。運用・バックアップ・デモ環境の構築がすべて単純になる。
- Streamlit Community Cloud（デモを公開するための無料サービス）にデプロイする際、追加のソフトを動かす必要がなくなる。
- 数値の並び（ベクトル）を事前に正規化（長さを1に揃える処理）しておけば、内積の計算結果がそのままコサイン類似度（似ている度合い）になり、計算がシンプルになる。

## 検討した代替案

| 案 | 却下理由 |
|---|---|
| FAISS（専用のベクトル検索ソフト） | 1,000件規模では近似検索を使う意味がない。索引の構築・保存の手間が増えるだけ |
| Chroma / Qdrant等 | 別のプログラムを起動しておく必要がある。デプロイの構成が複雑になり、デモ当日にトラブルが起きる箇所が増える |
| pgvector | PostgreSQL（別の本格的なデータベース）の導入が必要。同上の理由で却下 |

## 結果

- **規模に対して適切な技術を選んだ**という判断そのものが説明材料になる。「なぜ専用のベクトル検索ソフトを使わないのか」と問われた場合に答えられる。
- 文書数が数万件規模になった場合は再検討が必要である旨を、本番フェーズの課題として記録する。
- 数値の並び（ベクトル）は事前にまとめて計算してデータベースに保存しておく。**検索するタイミングで、文書側の計算をやり直すことはしない。**

# ADR-0005 文章の意味を数値に変換するAIモデル（埋め込みモデル）の選定

**ステータス：起票（未承認・次回MTGで承認予定）**

## 文脈

日本語のニーズ文（生活者の言葉）とシーズ文（研究所の言葉）を、同じ基準で数値に変換できるAIモデルが必要。かつ、使うたびに料金が発生しない・普通のパソコン（CPU）で動く・デモで待たされない速さ、という条件がある。

## 決定

`intfloat/multilingual-e5-small` を第一候補とし、sentence-transformers（AIモデルを簡単に使えるツール）で自分のパソコン上で動かす。日本語特化の比較対象として `cl-nagoya/ruri-small` を実際のデータで試し、デモ用の文章の組み合わせで、より良い検索結果が出た方を採用する。

## 理由

- どちらも普通のパソコン（CPU）で動作し、**使うたびの料金がゼロ**。予算の制約とインターネットなしでも動かせることの両方を満たす。
- 小さいサイズのモデル（1つの文章を384個の数値で表す）なので、1,000件分をまとめて変換する処理が現実的な時間で終わる。
- multilingual-e5は多言語（日本語以外の言語）にも対応しているため、将来「海外展開する場合にも使える」という説明につなげられる。

## 実装上の注意

- **このモデルは、文章の前に決まった一言を付ける必要がある。** 検索する側の文章には `query: `、検索される側の文章には `passage: ` を付けないと、精度が大きく落ちる。付け忘れてもエラーにはならず、静かに性能が落ちるだけなので、**テストで確認する仕組みを用意する。**
- `normalize_embeddings=True`（数値の並びの長さを1に揃える設定）で保存する（ADR-0004の前提）。
- ruriを採用する場合、文章の前に付ける一言のルールが異なるため、モデルを切り替える際は要確認。

## 検討した代替案

| 案 | 却下理由 |
|---|---|
| OpenAI text-embedding-3 等、外部サービスのAPI | 使うたびに料金が発生する。ネットワークが不安定だとデモの障害点になる |
| multilingual-e5-large（より大きいモデル） | 普通のパソコンでの処理が重く、まとめて変換する処理もデモ中の応答も遅くなる |

## 結果

- モデル選定の最終判断は、実際のデータを入れたあとの検索品質の評価（デモ用の文章の組み合わせが上位に来るかどうか）で行う。この評価をスケジュールに組み込む。

# ADR-0006 双方向に検索できるようにし、似た文書と反対側の文書を分けて表示する

**ステータス：起票（未承認・次回MTGで承認予定）**

## 文脈

引き継いだ2つの資料で方向性が食い違っていた。

- docx 4-2：双方向（ニーズ→シーズ、シーズ→ニーズの両方向）。「双方向であることが現場に根付く条件。片方向だと、マーケ側が研究所側を検索するだけの道具になり、研究所側にはこのツールを使う理由が生まれない」
- pptx：ニーズ→シーズ方向のみを想定している

加えて、docxのサンプルコード`cross_search`は**反対側だけ**を検索対象にしている（`target = 'seed' if query_side == 'need' else 'need'`）。同じ側の文書は検索結果に出てこない仕組みになっている。

## 決定

1. **検索は双方向とする。** ニーズの文章からシーズ（技術）を、シーズの文章からニーズ（悩み）を、それぞれ検索できるようにする。
2. **同じ側の結果も返す。** ニーズの文章で検索した場合、近いニーズの文書（＝似た悩み、既存の訴求文言）と、近いシーズの文書（＝関連する技術）の両方を返す。
3. **同じ側と反対側は、それぞれ別々に検索を実行し、それぞれ別々に統合し、それぞれ別のカラム（表示欄）に表示する。1つの順位表に混ぜない。**

画面②は左右2カラム構成とする。左＝同じ側（似た悩み・既存の訴求）／右＝反対側（技術シーズ）。

## 理由

**双方向にする理由**

- 片方向だと研究所側にはこのツールを使う動機が生まれず、現場に根付かない。
- プログラム上のコストはほぼゼロ。検索対象を切り替える設定を1行変えるだけで済む。

**分けて実行・分けて表示する理由（こちらが本質的な理由）**

- 同じ側の文書は使われている単語が一致しやすいため、キーワード検索も意味検索も高いスコアを出しやすい。**1つの順位表に混ぜると、同じ側の結果が上位を独占してしまい、反対側＝この提案が本当に見せたい価値が埋もれてしまう。**
- 混ざった結果は、単なる「よくある検索」に見えてしまう。「0件→3件」というデモの核心が伝わらなくなる。
- 分けておけば、右側のカラムだけで、検索方式を切り替える効果（0件→3件になる様子）を見せられる。

## 結果

- `cross_search`（検索処理）は、同じ側・反対側の2本の検索を実行する仕様に変更する。docxのサンプルコードは修正が必要。
- **デモの台本で主役として使うのは、ニーズ→シーズ方向のまま**とする。両方向をすべて台本に含めると、パート3の90秒という時間枠を超えるため。反対方向は画面を見せる程度にとどめる。
- **データを準備する作業の完了条件に「両方向の実例の組み合わせを、実際に収集したデータの中から各1組以上見つけられていること」を加える。** ニーズ→シーズ方向は「ベタつく × 可塑化」の組み合わせが確保済みだが、シーズ→ニーズ方向の良い実例はまだ見つかっておらず、ここが弱いと双方向であることを説明した瞬間に説得力が薄くなってしまう。
- 同じ側の表示件数は、主役である反対側の結果を埋もれさせない範囲（左右各3件程度）とし、実装後に調整する。

# ADR-0007 「過去の使われ方」を表示する内容を、実現できる形に定義し直す

**ステータス：起票（未承認・次回MTGで承認予定）**

## 文脈

pptx Slide 14 は、検索結果として次の3つを返すとしている。

1. 使えそうな技術
2. その根拠となるデータ
3. **過去の使われ方**（どの商品で、どんな訴求文言に使ったか）

そして「3つ目がこの企画の肝」としている。理由は、「同じ訴求で既に商品を出していたなら差別化にならず、逆に技術はあるのにまだ使われていない切り口があれば、そこが新しい商品の独自性になる」という考え方である。

しかし実装する上で、2つの問題がある。

- データを保存する`documents`テーブルに、この情報を入れる場所（列）がない（`doc_type / source / title / body / url / pub_date / category / dept` しかない）
- **「どの技術がどの自社商品に使われたか」という情報は、社外に公開されているデータからは原理的に手に入らない。** 社内の企画書データベースが必要であり、今回のデモ用の環境にはそれが存在しない。

## 決定

「過去の使われ方」として表示する内容の定義を、以下のとおり変更する。

- **旧：** その技術が、どの商品で、どんな訴求に使われたか → 公開データでは実現不能
- **新：** その悩みに対して、すでに存在している訴求・解決策 → 実現可能

ADR-0006で「同じ側の結果も返す」仕様にしたため、この情報はニーズ側の検索結果として自然に手に入る。ニーズ側で収集するデータには商品ページの訴求文言も含まれている（docx 7-6 の収集経路②）ため、「同じ悩みに対して、すでに市場に出ている訴求文言」が検索結果として返ってくる。

## 理由

- 実現可能であり、かつ「差別化のヒントになる」という**当初の目的をそのまま満たす。**
- 検索結果には自社の訴求だけでなく他社の訴求も含まれる。競合が既に同じ訴求で商品を出しているかどうかも分かるため、差別化を考える材料としてはむしろ実務的に強い。
- 新しくデータの保存場所（テーブル）を作る必要も、既存のデータ構造を変える必要もない。同じ側の検索の副産物として得られる。

## 検討した代替案

| 案 | 却下理由 |
|---|---|
| 「技術↔商品↔訴求」の対応表を新しく作り、手作業で紐付ける | データが手作りになり、「都合よく作ったのでは」という疑いを招く。実際に収集したデータで信頼性を示す方針に反する |
| この機能自体を諦め（Won't）、pptx Slide 14 から3つ目の項目を削除する | 差別化のヒントを示すという、この企画の重要な要素がそのまま失われる。企画の価値が下がる |

## 結果

- **pptx Slide 14 の3つ目の項目の文言修正が必要。** 担当と期限を決める。
- 本番フェーズでは社内の企画書データベースを接続し、元の定義（技術↔商品↔訴求）を実現する、という将来の拡張案として記録する。
- 効果を測る指標「過去の使われ方の参照回数」は、「同じ側のカラムに表示された文書をクリックした回数」として定義する。

# ADR-0008 「該当する技術が社内にない」の判定を、反対側の検索結果だけで行う

**ステータス：起票（未承認・次回MTGで承認予定）**

## 文脈

展開構想⑤（検索ログが次のR&D投資テーマを示す、というアイデア）と画面③のダッシュボードは、「検索してもヒットしなかったクエリ＝社内に存在しない知見のリスト」という定義に依存している。

しかし意味検索（ベクトル検索）は、似ている度合いの上位k件を**常に返す。** 何も工夫せずに実装すると「0件」という状態が構造的に発生せず、ダッシュボードが機能しない。

さらにADR-0006で同じ側の結果も返すようにしたため、同じ側は使われている単語が一致する文書が必ず存在し、なおさら「0件」にならない。

## 決定

「ヒットなし」の判定は、**反対側の結果に対してのみ**行う。判定基準は以下の2条件を両方満たす場合とする。

1. 反対側のキーワード検索（BM25）でヒットが0件
2. 反対側の意味検索（ベクトル検索）で、もっとも近い文書の類似度（コサイン類似度）が、あらかじめ決めた基準値未満

基準値は実際のデータを入れたあとに決定する。ひとまず暫定値として0.80を置き、デモ用の文章の組み合わせでは「ヒットあり」、無関係な検索文章では「ヒットなし」と正しく判定される水準に調整する。

## 理由

- 「ヒットなし」の意味を **「その悩みを解決できる技術が社内にない」** という状態に限定できる。これは展開構想⑤の「社内に存在しない知見＝次のR&D投資テーマの候補」という説明とぴたり一致する。
- 同じ側を判定から除外することで、「似た悩みは見つかるが、それを解決する技術がない」という、最も価値のある状態を正確に見つけられる。
- キーワード検索の結果だけで判定すると、単語が違うだけで実は技術が存在するケースまで「ヒットなし」に数えてしまう。これは本企画が解決したいまさにその課題であり、誤って「ヒットなし」に数えてはいけない。

## 結果

- `search_logs`（検索の履歴を記録する表）の`hit_count`（ヒット件数）には**反対側のヒット数**を記録する。同じ側のヒット数は別の列（`same_side_hit_count`）にするか、記録しないかは、データ構造を確定するタイミングで決める。
- 基準値を決める作業をスケジュールに含める。基準値が不適切だと、ダッシュボードが空になるか、逆にすべてが「ヒットなし」になってしまう。
- 基準値を画面上で調整できるようにはしない（対応しない）。デモ中に触れる余地を作ると、恣意的に見えてしまう。

# ADR-0009 ログイン機能・権限管理は作らず、立場を選ぶボタンで代用する

**ステータス：起票（未承認・次回MTGで承認予定）**

## 文脈

docx 7-7 でログイン機能・権限管理は対応しない（本番での要件として言及のみ）と宣言されている。3週間という期間を考えれば妥当な判断である。

しかし、ログイン機能がないと以下が成立しない。

- ADR-0006の双方向検索：利用している人がニーズ側（マーケ）かシーズ側（研究所）かが分からないと、どちら方向に検索すればいいか決められない
- 効果を測る指標「部門をまたいで検索した割合」：`search_logs.user_dept`（検索した人の所属部門を記録する列）の値が取得できない

## 決定

ログイン機能・権限管理は実装しない。代わりに画面上部に**立場を切り替えるボタン（R&D ／ マーケ）**を置き、選んだ内容をその場のセッション（画面を開いている間だけ保持される情報）に保持する。この値を、検索方向の決定と `user_dept` の記録の両方に使う。

このボタンは必須（Must）とする。

## 理由

- 1つの画面要素で、2つの要件（検索方向を決めること、効果測定の値を取得すること）を同時に満たせる。
- デモにおいて、立場を切り替えると検索の向きが変わることを目に見える形で示せるため、「双方向である」ことの説明にもなる。
- 権限管理を「あえて対象外にした」と明示することは、想定される質問Q4（「部門を越えて情報を見せていいのか」）への回答としてそのまま使える。あいまいにするより、線を引いて示すほうが説明しやすい。

## 結果

- 「部門を越えて情報を見せていいのか」という質問には、**権限管理は本番フェーズで対応する要件であり、今回の試作版ではあえて対象外とした**と回答する。この回答を想定質問集に明記する。
- 立場を切り替えるボタンの選択内容はセッション単位（画面を開いている間のみ）。画面を再読み込みすると初期値に戻る仕様とし、デモの手順書に初期状態を明記する。

# ADR-0010 検索結果の「一致度・関連度」の数値をどう出すか

**ステータス：起票（未承認・次回MTGで承認予定）**

## 文脈

pptx Slide 13 は検索結果に「一致度 92%」「一致度 85%」といったパーセンテージを表示している。

しかしADR-0003で採用した統合方式（RRF）のスコアは、順位の逆数を足し合わせた値であり、上位でも0.03程度にしかならない。**パーセンテージとして表示できる数値ではない。** そのまま100倍しても意味を持たない。

また「一致度」という言葉は、「システムが正しさ・適合性を判定している」という印象を与えてしまい、想定質問Q8（「AIが実現可能性を判定しているのか」）を自ら誘発してしまう。

## 決定

1. **並び順は統合方式（RRF）で決める。表示する数値は意味検索側の類似度（コサイン類似度）とする。** 両者は役割を分ける。
2. 類似度をパーセンテージに変換して表示する。変換の計算式は実際のデータを見て決める（そのままの値を100倍すると、無関係な文書でも70%台の数値が出てしまい意味をなさないため、表示する範囲の調整が必要）。
3. **表記は「一致度」ではなく「関連度」とする。**
4. キーワード検索だけでヒットした文書（意味検索側には出ていない文書）はスコア表示を省略し、「語一致」等のラベルを付ける。

## 理由

- 統合方式（RRF）は複数の検索方式の順位をまとめるための仕組みであり、文書とクエリ（検索文章）がどれくらい近いかを表す量ではない。並び順の決定には使い、近さの表示には使わない、という役割分担が正しい。
- 「一致度」は「判定している」というニュアンスを帯びる。「関連度」であれば、**このアプリが返しているのは関連する過去の資料であり、判断するのはあくまで人間**という提案の方針と矛盾しない。
- 変換の計算式を実際のデータで決めることで、「92%とは何の92%か」と問われても答えられる。

## 検討した代替案

| 案 | 却下理由 |
|---|---|
| 数値を表示しない | pptxの画面案から後退してしまう。順位だけだと結果の説得力が落ちる |
| 統合方式（RRF）のスコアを正規化して表示する | 上位1件が常に100%になるなど、値が検索対象の文書集合によって不安定になる |

## 結果

- 検索時に意味検索側の類似度を保持しておき、統合後も参照できるようにする。
- pptx Slide 13 の「一致度」表記を「関連度」に修正する。
- 変換の計算式を決める作業をスケジュールに含める。

# ADR-0011 日本語の文章を検索用に単語へ分割する方式

**ステータス：起票（未承認・次回MTGで承認予定）**

## 文脈

SQLiteのFTS5（全文検索の機能）で日本語を扱うには、文章をどう単語に分割するか（トークナイズ方式）を選ぶ必要がある。docx 7-3 では「3文字ずつ機械的に切る方式（trigram）」を第一案とし、「Janome（日本語を単語ごとに分割するツール）で分かち書きするなら別の方式（unicode61）でも可」と併記している。

ここには**デモの成否に直結するリスク**がある。

デモの核心は「キーワード検索で0件 → 両方併用で3件」という流れである。3文字ずつ機械的に切る方式（trigram）は、「夕方になると前髪がベタッとして束になる」という検索文章から「になる」「して」「のて」といった**意味を持たない3文字の断片**を作り出してしまう。これらの断片が技術論文側にたまたま含まれていれば、**キーワード検索が0件にならない。**

0件にならなければ、デモの核心が成立しない。

## 決定

Janome（日本語を単語ごとに分割するツール）で文章を単語に分解し、品詞フィルタ（名詞・動詞・形容詞だけを残し、助詞・助動詞・記号を取り除く処理）を適用したうえで、`unicode61`（一般的な単語単位のトークナイザ）を使用する。

3文字ずつ機械的に切る方式（trigram）は不採用とし、うまくいかない場合の代替手段としてのみ記録する。

## 理由

- **「0件になる」ことを設計であらかじめ保証できる。** 品詞フィルタを通すと、検索文章側の単語は「夕方」「前髪」「ベタッ」「束」等の意味のある単語だけになり、技術論文とたまたま一致する確率が大幅に下がる。
- W4で文章の正規化・単語分割の仕組みを実装済みであり、その資産をそのまま使える。新たに追加する部分は品詞フィルタのみ。
- 検索結果が説明可能になる。なぜこの文書がヒットしたのかを、一致した単語で説明できる。

## 検討した代替案

| 案 | 却下理由 |
|---|---|
| 3文字ずつ機械的に切る方式（trigram） | 意味を持たない断片で偶然ヒットしてしまい、デモの前提（0件になること）が崩れる可能性がある。制御できない |
| MeCab + IPAdic（別の単語分割ツール） | 辞書のインストールが必要でデプロイが重くなる。Janomeはpure Python（追加ソフト不要）で依存が軽い |

## 結果

- **デモ用の検索文章でキーワード検索が実際に0件になることを、テストとして明示的に確認する。** これは「動けばよい」というレベルの話ではなく、デモが成立するための必須条件である。
- 品詞フィルタでどの品詞を残すかは、実際のデータで調整する。フィルタが強すぎると、通常の全文検索としての再現率（ヒットすべきものをどれだけ取り漏らさないか）が落ちる。
- 万一Janomeの導入がデプロイ環境で問題になった場合の代替として3文字方式（trigram）を残すが、その場合はデモ用検索文章の「0件」をストップワード（意味のない単語を除外するリスト）で別途保証する必要がある旨を記録する。

---

# ADR-0012 J-STAGE（論文検索API）の使い方と規約対応

**ステータス：起票（未承認・次回MTGで承認予定）**

## 文脈

docx 7-6 において、シーズ側（研究所側の技術情報）の収集対象として、J-STAGE（学術論文を検索できるAPI）が補助的に挙げられている。同時に、docx自身が以下の警告を記載している。

> 取得データのキャッシュを24時間までに制限する条項があるため、恒久DBに貯め続ける設計は規約に触れる可能性がある。利用前に規約原文の確認が必須

docxが示した対策は「発表で公開データはデモ用の代替と明示し、デモ後にデータを削除する運用にする」というものだが、これは**プログラムの仕組みではなく、人間の運用でカバーする**方法であり、設計としては弱い。3週間という期間で規約解釈のリスクを抱えるのは避けたい。

## 決定

1. J-STAGE APIを**本文データの恒久的な保存には使用しない。**
2. シーズ側の収集は、企業の研究開発情報ページ・技術系ニュースリリース・学会発表一覧を実際に集める（クロール）ことを主な方法とする。
3. J-STAGEを使う場合は、書誌メタデータ（タイトル・著者・掲載誌・URL）を参照するだけにとどめ、本文の蓄積は行わない。
4. 利用する場合は「Powered by J-STAGE」の表示を画面に載せる。
5. **実装に着手する前に、規約の原文を確認する担当と期限を決める。**

## 理由

- 規約の解釈リスクを、人間の運用ではなく設計そのもので回避する。
- docx 7-6 の記述でもJ-STAGEは「補助」であり、主な収集対象は企業の研究開発ページ等である。主な対象だけで目標データ量（シーズ300〜500件）を満たせるなら、リスクを取る理由がない。
- 発表時に「規約を確認したうえで、蓄積対象から外した」と説明できることは、むしろ設計判断としてプラスに評価される。

## 併せて確定した収集方針

| 対象 | 扱い | 根拠 |
|---|---|---|
| 企業の研究開発ページ・技術ニュースリリース・学会発表一覧 | **シーズ側の主な収集対象** | 公開情報。robots.txt（クロールしてよい範囲を示すルール）を守り、アクセス間隔を確保する |
| 化粧品会社のFAQ・お客様サポートページ | **ニーズ側の主な収集対象** | 生活者の困りごとが、生活者自身の言葉で書かれている |
| 商品ページの訴求文言 | ニーズ側に含める | ADR-0007の「既存の訴求」の供給源 |
| J-STAGE | 書誌メタデータのみ | 本ADR |
| EC・口コミサイト（@cosme、Amazonレビュー等） | **収集しない** | 利用規約で自動収集（クロール）が禁止されていることが多い |
| J-PlatPat／特許データベース | **対象外** | 自動収集ができない。全文キーワード検索にも向かない。本番フェーズの拡張案として記録する |

## 結果

- 規約確認の担当と期限を決める（未定）。
- デモ用シーズ文書（「皮脂による毛髪の可塑化…」に相当するもの）が、J-STAGE以外の方法で取得できるかを早期に確認する。**取得できない場合、デモの核心が成立しないため、これは最優先の確認事項である。**

# ADR-0013 検索結果を見た人が「理解できない・使い方がわからない」問題をどう解決するか

**ステータス：保留** — 次回MTGの論点。TAからの指摘を受けて起票。

## 文脈

TAより以下の指摘を受けた。

> 語彙も異なっているような人が検索結果を見ても理解できるのか？どう使うかイメージできるのか？そこにもGAPが出てしまうイメージはありますね。その行間をどう埋めるのか？そこが工夫するポイントになるような気がしました

現在の設計は、検索がうまくいくこと（0件→3件になること）は証明できるが、**検索結果を受け取ったマーケ担当者が、それを見て何をすればいいか**までは設計していない。

検索結果として返るのは「皮脂による毛髪の可塑化を抑制する高分子被膜の設計」といった専門的な技術文書である。これを読んだマーケ担当者が、自分の企画に使えるかどうかを判断できる保証がない。**「検索がうまくいくこと」と「実際に価値が生まれること」の間にギャップがある。**

さらにこれは、docxが自ら引いた線とも表裏一体の関係にある。

> このアプリは「可否を判定」しない。返すのは関連する過去の資料であり、判断するのは人間のまま

「AIは判定しない」と宣言した以上、**「材料を渡された人がちゃんと判断できる」ことは提案側が責任を持って用意する必要がある。** 現状その手当てがない。想定質問Q8（AIが判定するのか）の裏返しとして、「では受け取った人は何が分かるのか」という質問は発表で必ず来る。

## 選択肢

| 案 | 内容 | 効果 | コスト・リスク |
|---|---|---|---|
| A. 要約を追加する | AI（LLM）で技術文書を生活者の言葉に言い換えて併記する | 大 | **ADR-0005（料金ゼロ・自分のパソコンだけで完結させる方針）と衝突する。** 要約に誤りがあると企画の判断を誤らせ、提案の信頼性を損なう。応答速度も落ち、トラブルの起こる箇所も増える |
| B. ヒットした理由を示す | なぜこの文書がヒットしたかを、元の文章からの抜粋で示す | 中〜大 | 低い。**AIが新しく文章を作らないため、誤った情報が混ざる心配がない。** docxではCould（あれば良い）⑧として記載されている |
| C. 人につなぐ | 文書の担当部署・著者を表示し、「誰に何を聞けばいいか」まで示す | 中 | 低い。`dept`（部署）の列は既にデータ構造にある |
| D. 用語集を用意する | 専門用語と生活者の言葉の対応表を用意する | 小 | 中程度。作る手間の割に効果が薄い |

## 論点

- **B＋Cを採用し、Aは対応しない（Won't）として理由を説明する**のが、3週間という制約と「AIは判定しない」という方針の両方に合っていると考えられる。B・Cはいずれも、AIが新しく文章を作る（生成する）方式ではないため、誤った情報が混ざる心配なしに「わかりにくさを埋める工夫」を説明できる。
- Cは、想定利用者像「ペルソナB」の課題「誰に聞けばいいか探す必要もない」に直接対応し、「研究所に相談する前に当たりをつける」という提案の説明の仕方とも矛盾しない。検索の出口として自然な形である。
- Aを採用する場合、ADR-0005の見直しが必要になる。またAI特有の間違い（ハルシネーション）への対策として、元の文章を必ず併記する必要がある。
- Bを採用する場合、意味検索は文書単位で似ている度合いを出すため、**文書の中のどの部分が近いのかを示すには、文単位・段落単位に分割する必要が出てくる**可能性がある。実装コストの見積もりをやり直す必要がある。

## 決定への影響範囲

- 採用する場合、docx 7-7 の優先順位表でCould（あれば良い）⑧だったものが、必須（Must）に格上げされる
- 画面②の設計が変わる（検索結果カードに、抜粋・担当部署を表示する場所が必要になる）
- 発表のパート3-1に「わかりにくさをどう埋めるか」の説明が1つ増える

# ADR-0014 どこまで自動化するか（企画書作成なども自動化するか）

**ステータス：保留** — 次回MTGの論点。TAからの指摘を受けて起票。

## 文脈

TAより以下の発言があった。

> 企画書〜実験計画〜簡易シミュレーション、過去検討からの論点出しくらいまで自動でやって欲しいですね〜（ぼそっ）

また、商品企画とR&Dの知見をつなぐ事例として、サッポロのアプリ（たっきーが以前紹介したもの）との類似が指摘された。

現在のスコープ（今回作る範囲）は検索の仕組みであり、企画書の自動作成・実験計画の立案・シミュレーション・論点出しはいずれも含まれていない。

## 論点

- **3週間・3名という制約の中では、これらは明確に今回の範囲外である。** 検索の精度とデモの成立に力を集中すべきというのが現在の前提。
- ただし、ADR-0013の指摘と本件は**同じ方向を指している可能性が高い。** つまり「検索して結果を返すだけでは物足りない」という評価が背後にある。この見立てが正しければ、今回の範囲を守るだけでは評価が上がらない。

  - (a) 将来の展開構想に「検索の先の自動化」という項目を明示的に追加し、今回はやらない理由と、将来どうつながるかを説明する
  - (b) 「過去検討からの論点出し」だけを、ADR-0013のB案（ヒットした理由を示す機能）の延長として部分的に実現する
  - (c) 完全に対応しない（Won't）として、その理由を明示する
- **サッポロのアプリの内容を、たっきーに確認する必要がある。** 類似が指摘された以上、何がどこまで似ているのか、差別化できる点はどこかを把握しておかないと、発表で比較された際に答えられない。

## 未確認事項

- サッポロのアプリの具体的な機能範囲（要確認：たっきー）
- TAの発言が、評価の基準としての要求なのか、将来こうなってほしいという期待なのか

## 決定への影響範囲

- (b)を採る場合、実装する範囲が増える。ADR-0013とセットで判断する必要がある

# ADR-0015 データの再現性と共有方針（3人でどう同じデータを使うか）

**ステータス：起票（未承認・次回MTGで承認予定）**

## 文脈

3名がClaude Codeを使って並行して開発する。全員が同じデータで動作確認できる状態が必要になる。

同時に、この企画には固有の事情がある。**デモの核心である「キーワード検索で0件 → 両方併用で3件」という結果は、特定のデータの組み合わせの上でしか再現しない。** インターネットから情報を集める処理（クロール）は実行するたびに結果が変わり、対象サイトの内容が更新されれば取得内容も変わる。各自が自分のパソコンでクロールすると、3人が微妙に違うデータを持つことになり、「ぐんさんの環境では3件出たが、本番環境では2件」という事態が起こりうる。

つまり解くべき問題は2つあり、性質が異なる。

1. **共有** — 3人が同じデータで作業できること
2. **凍結** — デモで使うデータが変化せず、本番でも確実に同じ結果が再現すること

## 決定

1. **SQLiteの`.db`ファイル（データが入った実体）はGit（変更履歴を管理する仕組み）で管理しない。** `.gitignore`（Git管理から除外するファイルの設定）に`*.db`を追加する。
2. **再現するための手順をコミット（Gitに保存）する。** データの構造の定義（`schema.sql`）、データを集めるプログラム（クローラ）のコード、収集対象のURLリスト、データを取り込むスクリプトをリポジトリ（プログラムを保管する場所）に置き、`git clone`（プログラム一式を手元に取得すること）した後にスクリプトを1本動かすだけで、空の状態からデータベースが作れる状態にする。
3. **デモ用の固定データはスナップショット（ある時点の状態を切り取って保存したもの）として固定し、リポジトリにコミットする。** 収集したデータのうちデモに使う数十件を`fixtures/`（テスト・デモ用の固定データを置く場所）にJSON形式で保存する。往復両方向の実例の組み合わせ（ADR-0006の完了条件）を必ず含める。
4. 通常の全データ（シーズ300〜500件、ニーズ300〜500件）は各自が自分で生成する。共有しない。
5. 生成済みのデータベースを共有したい場合は、クラウドストレージ（オンラインの保管場所）に置き、リポジトリにはダウンロード手順のみ記載する。
6. **Streamlit Community Cloudへのデプロイ時は、アプリの起動処理の中で`.db`を自動的に組み立てる。** アプリが起動したとき、`.db`がまだ存在しなければ`schema.sql`でテーブルを作成し、`fixtures/`のJSONを読み込んで投入する。以降はその実行環境（コンテナ）の中に存在するローカルファイルとして、そのまま検索処理に使う。

## 理由

**`.db`をコミットしない理由**

- SQLiteのデータファイルはバイナリ（文字として読めない形式）であり、Gitは差分（何が変わったか）を取れない。1件のデータを更新するだけでも、ファイル全体が変更履歴として積み重なっていく。今回は数値の並び（ベクトル）もバイナリデータとして持つため、1万件規模で数十MBになり、クロールのたびにコミットするとリポジトリが数百MBに膨らんでしまう。そしてGitの変更履歴は簡単には削除できない。
- **3人が並行して作業していると、内容が競合（コンフリクト）した場合に解決できなくなる。** バイナリファイルは内容をマージ（統合）できず、どちらかを丸ごと捨てるしかない。クローラを回して更新したデータベースと、画面確認用に触ったデータベースが競合すると、片方の作業がそのまま消えてしまう。

**デモ用データを固定する理由**

- クロール結果の変動は制御できない。デモの再現性を保証する唯一の方法が、ある時点の状態を切り取って固定しておくこと（スナップショット）である。
- テキスト形式（JSON）で数十件程度であれば、変更内容の差分も取れて、サイズも小さい。Gitの利点をそのまま活かせる。
- **変更履歴として管理しておくことで、誤って壊してしまっても元に戻せる。** これが、後述するクラウド共有データベース案に対する決定的な優位点になる。

**起動時に自動組み立てにする理由**

- Streamlit Community Cloudの実行環境は、専用の永続データベースを持たない使い捨てのコンテナである。手動で`.db`をアップロードしても、コンテナが再起動・スリープから復帰すると消えてしまう。起動時に`fixtures/`から自動で組み立てる形にしておけば、何度再起動されても同じ初期状態が確実に再現される。
- この方式は、決定1〜3（`.db`は管理しない、手順はコミットする、デモ用データは固定する）をそのままクラウド環境に適用しただけであり、新しい仕組みを追加する必要がない。

## 検討した代替案

| 案 | 評価 |
|---|---|
| **Supabase等のクラウド共有データベース** | 「共有」の問題は確かに解決する。しかし「凍結」の問題は**むしろ悪化する。** 1つのデータベースをみんなで書き換える形になるため、誰かが発表前日にクローラを再実行すると、デモ用データを上書きしてしまい、元に戻す手段がない。加えてデモ当日にインターネット接続が必要になり、また今回のキーワード検索の仕組み（FTS5）が使えないため、ADR-0011（Janome＋品詞フィルタで「0件」を保証する設計）をそのまま移せない。**却下** |
| `.db`ファイルを直接Gitにコミットする | リポジトリが肥大化し、競合も解決できなくなる。**却下** |
| Git LFS（大きなファイルをGitで扱う仕組み） | `.db`を共有する手段としては妥当だが、今回の規模ならスクリプトで作り直す方がシンプル。**採用しない** |
| 全員が毎回自分でクロールし、データの違いは受け入れる | デモの再現性が保証されない。**却下** |

## 結果

- `fixtures/`（固定データを置く場所）に何を入れるかを選ぶ作業が発生する。ADR-0006の「往復両方向の実例の組み合わせを各1組以上確保する」と同じタイミングで行う。
- テスト（デモ用の検索文章でキーワード検索が0件になることの確認、ADR-0011）は、`fixtures/`の固定データに対して実行する。毎回変わる通常のデータに対しては行わない。**これによりテストの結果が安定する。**
- 発表用の環境では`fixtures/`のデータが確実に投入されていることを、デモ手順書のチェック項目に入れる。
- Streamlit Cloudのコンテナは同時アクセスしている全員が同じ実行環境（同じ`.db`）を見る構成であるため、立場トグル（ADR-0009）はセッションごとの見え方の切り替えであり、データ自体は共有されている。この前提をデモ手順書に明記する。
