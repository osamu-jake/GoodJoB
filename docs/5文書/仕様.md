# 仕様 — 知の越境検索（PROJECT ZERO / W6）

前提: Streamlit単一プロセスのPoC（Streamlit Community Cloudにデプロイ）。フロント・検索ロジック・
ログ記録を同一プロセスで実行し、Next.js＋FastAPIのような層分離は行わない。

## 全体像
マーケ担当者／研究員がタブ①検索に企画案の文章（検索語ではなく文章）を入力すると、Janome＋品詞
フィルタでトークナイズしたBM25検索と、`multilingual-e5-small`によるベクトル検索を実行し、RRF
（k=60、各方式上位50件→統合後上位10件）で統合した結果を、関連度順の統一カードリストとして返す
（ADR-0017）。各カードには一言要約・一致理由・権利状況・使用実績を表示する。タブ②技術データベース
では技術一覧を絞り込み・詳細閲覧できる。データは事前に投入されたSQLite（`documents` /
`embeddings` / `projects` / `project_techs` / `project_products` / `patents` / `search_logs`）を参照し、検索時に新たな生成AI呼び出し
は行わない（要約は登録時に1回のみ生成・保存）。反対側の結果の下には、同じ側の結果を折りたたみで
最大3件だけ別枠で表示する（ADR-0024）。**タブ①の検索方向はニーズ→技術の片方向に固定**し、立場・所属部署の選択UIは設けない
（利用者はマーケ／商品企画の1種類だけ。ADR-0028・0030）。
「この技術は何に使えるか／差別化の余地はあるか」はタブ②の詳細画面が担う（ADR-0029）。参照するテーブルは`documents`／`embeddings`／`projects`／
`project_techs`／`project_products`／`patents`／`search_logs`の7つ（企画系の3つはADR-0039で`tech_usage`・`evaluations`から置き換え）。

## 画面・操作

### タブ①検索（デモの主役）
- 検索方式トグル（キーワードのみ／意味のみ／両方併用）。**デモ専用の控えめな帯**に置き、通常画面
  には出さない（F-06・F-10）
- 検索窓：企画案の文章をそのまま入力する（例：「夕方になると前髪がベタついて束になる、という
  20〜30代男性の不満に応えたい…」）。短い単語より文章の方がベクトル検索の精度が出る
- 検索結果カードリスト（関連度順、F-03）。カード1件の表示項目：
  - 技術名／文書タイトル、`doc_type`ラベル（シーズ／ニーズ）
  - 関連度（**コサイン類似度の百分率**。結果セット内での相対値にはしない。ADR-0035）。
    相対値にすると1位が必ず上限値になり、無関係なクエリでも「96% 近い」と出て、
    「ヒットなし」の警告と同時に表示される自己矛盾が起きるため
  - **この技術が解決しようとしている課題**（`problem`。発明者自身の言葉なので、企画側が「自分の
    ニーズに効くか」を判断する主材料になる。ADR-0021）
  - 一言要約（シーズ側のみ。F-16、「※AIによる要約です」注記付き）
  - 一致理由ハイライト（語句単位。F-18）
  - 権利状況バッジ（登録済／出願中／未出願。F-19）
  - 使用実績サマリ（採用実績の有無＝`project_techs`に`decision='adopted'`の行があるか。F-08への導線。ADR-0039）
  - 「エビデンス・使われ方を見る」ボタン（詳細画面へ遷移。F-05・ADR-0047。原文URLへの直接リンクは置かない）
- **「ヒットなし」判定（ADR-0008）でも画面は空にしない。** ベクトル検索は仕組み上つねに上位N件を
  返すため、反対側でBM25=0件かつベクトル類似度が基準値未満の場合も、関連度%が低い「応用できるか
  もしれない候補」としてカードは示される。この場合は固定の案内文（「十分に一致する技術は見つかりません
  でした。関連度の低い候補は下に折りたたんでいます。」）を表示し、**候補カードは折りたたみ（「関連度の低い
  候補を見る（N件）」）に入れる。「似た悩み・既存の訴求」の折りたたみは出さない**（無関係な文でも的外れな
  カードや訴求が前面に並ぶのを避けるため。ADR-0052）。**言い換え候補の提示は次フェーズへ**（生成方法が
  未定義。ADR-0045）。裏側では`search_logs.hit_count=0`として記録され、
  その企画案がタブ②「まだ社内に無い技術」に個別の1件として追加される
- **「似た悩み・既存の訴求」の折りたたみ（ADR-0024・0031）。** 反対側のカードリストの下に別枠で置く。
  中身は2つ：
  - **①似た悩み**＝同じ側（ニーズ側）の検索結果を最大3件。1つの順位表には混ぜない（同じ側は必ず
    語が一致するため上位を独占し、主役の反対側が埋もれる）
  - **②この悩みに対して自社が既に打った訴求**＝反対側でヒットした技術のうち採用実績があるものの
    訴求（その技術を`adopted`にした企画の`project_products.claim`。商品名・訴求・上市年月。ADR-0039）。**同じ訴求で既に出ていれば差別化になりにくく、
    出ていなければ余地が残っている**という判断材料になる。**同じ商品・訴求は1回だけ表示する**（1企画で
    複数の技術を採用していると、ヒットした技術の数だけ同じ訴求が返るため。`project_products.id`で重複を除く。ADR-0039）
  - ①②の2点セットでADR-0007「過去の使われ方」を実現する（訴求は同じ側検索では取れず
    `project_products`にしか無いため。ADR-0031・0039）
- 「ヒットなし」判定はあくまで**反対側に対してのみ**行う。同じ側が何件返っても判定は変わらない
  （ADR-0008は変更なし）
- カードをクリックすると詳細が開く。**開き方（モーダル／画面切替／他）はぐんさんが実装しながら
  検討し、じゃけに提案して決める**（ADR-0034）。決まっているのは「`st.tabs`にはアクティブなタブを
  変えるAPIが無いのでタブ遷移では実現できない」ところまで。タブ②の一覧からも同じ部品を使う

### タブ②技術データベース
- 技術一覧。絞り込み条件：「未使用の技術」「特許 登録済／出願中」「まだ社内に無い技術」（F-17）。
  「未使用の技術」＝`project_techs`に`decision='adopted'`の行が1件も無い技術（ADR-0039）
- 「まだ社内に無い技術」は**頻度ランキングにしない**。個別の企画案を並べ、検索日と
  その時の最高関連度を表示する。各企画案は文面が毎回異なるため集計は実態に合わない。
  部署列は出さない（利用者が1種類で全行同じ値になるため。ADR-0030）
- 詳細画面：
  - エビデンス（**企画ごとの判断**（`project_techs`の採用／見送り／評価中と理由。行が
    無ければ「未評価」）・`patents`の関連特許）を同じ場所に並べる（F-05、ADR-0022・0039・0047）。
    **原文へのリンクはUIに置かない**（ADR-0047）。
    同じ技術が企画Xでは採用、企画Yでは見送りなら、その両方を並べる。「やって駄目だったか」「まだ評価されていない」ことも
    判断材料として明示する
  - 自社での使われ方（この技術を`adopted`にした企画と、その`project_products`の商品・訴求。F-08・ADR-0039）
  - **似た課題を解く技術と、その使われ方**（ADR-0029）。同じ側（seed→seed）の検索で近い技術を出し、
    各技術に採用実績（どの企画のどの商品にどんな訴求で、いつ使われたか。`project_products`）と企画ごとの判断
    （`project_techs`の採用／見送り／評価中。行が無ければ未評価）を併記する。**これが「この技術は何に使えそうか」の根拠になる。** 判定はせず記録を並べる
    だけで、「行けるかも」と同時に「そこは踏まれて駄目だった」「そこはまだ誰も見ていない」も渡す
  - 関連する収集済みの声（反対方向のクロス検索結果）。**「母集団を代表しません」と明記し、出典URLを
    付けて併記する。** 市場性の根拠としては使わない（声はダミー＋実在FAQ少数で代表性がない。ADR-0028）
  - ※訴求の競合チェック・空き地判定は今回のPoCでは対応しない（ADR-0019）

## 入力と出力

| 要件ID | 入力 | 処理 | 出力 |
| --- | --- | --- | --- |
| F-01 | 手動転記した特許（要約・背景技術・課題）、ダミーのニーズ文 | `doc_type`/`source`/`content_hash`を付与しDBへ格納。`body`/`problem`/`background`の3つをフィールドごとに埋め込み（`title`は埋め込まない。ADR-0021）。`summary_plain`は`knowledge.db`に入れておいた生成済みテキストをそのまま投入（ADR-0020・0025） | `documents`の行、`embeddings`の行（1文書につき最大3行） |
| F-02 | 企画案の文章、`query_side`（タブ①では`'need'`固定。ADR-0028。双方向のインターフェース自体は残しタブ②が使う） | `cross_search()`：**反対側**をBM25で上位50件、ベクトル（`query: `プレフィックス付き）を全フィールドのベクトルと比較し**doc_idごとに最大類似度を採用**して上位50件。**RRF（k=60）はどの文書を結果に含めるかの決定にのみ使い、並び順には使わない**（ADR-0023）。あわせて**同じ側**を同じ方式で最大3件だけ別に検索する（ADR-0024） | 反対側の文書リスト（doc_id, 関連度, 最も効いたフィールド名, BM25/ベクトルどちらでヒットしたか）と、同じ側の文書リスト（最大3件。1つの順位表には混ぜない） |

| F-04 | query, mode, user_dept, hit_count | `st.button`のブロック内でのみ`search_logs`へINSERT（Streamlitの再実行モデルに注意。ボタン外に書くと水増しされる） | `search_logs`の行1件 |

| F-06 | 検索方式選択（bm25／vector／hybrid） | `cross_search`内の統合ロジックを切替 | 結果件数・内容の変化（短文：0件→N件／長文：順位が入れ替わる。ADR-0026） |
| F-08 | doc_id（seed側） | `project_techs`を`seed_id`で検索し、`decision='adopted'`の企画の`project_products`を結合。あわせて同じ側検索で近い技術を取り、それぞれの採用実績・企画ごとの判断を結合（ADR-0029・0039） | 採用実績一覧（product, brand, claim, launched）と、似た課題を解く技術＋その実績・評価 |

| F-13 | 新規登録文書 | 反対側の既存文書との類似度が閾値超か判定 | マッチ一覧への追加通知 |

## データ

```sql
-- 文書本体
CREATE TABLE documents (
  id            INTEGER PRIMARY KEY,
  doc_type      TEXT NOT NULL,   -- 'seed' | 'need'
  source        TEXT NOT NULL,   -- 'patent_manual' | 'dummy' | 'faq' | 'placeholder'（実特許に差し替えるまでの仮データ）
  title         TEXT,
  body          TEXT,            -- 【要約】＝解決手段の記述
  background    TEXT,            -- 【背景技術】（seed側のみ。ADR-0021）
  problem       TEXT,            -- 【発明が解決しようとする課題】＝問題の記述。ニーズとの照合に最も効く（ADR-0021）
  url           TEXT,
  pub_date      TEXT,
  category      TEXT,            -- ヘアスタイリング / スキンケア ...
  dept          TEXT,            -- 'R&D' | 'MK'（本番機能。PoCでは非表示）
  summary_plain TEXT,            -- 「平たく言うと」要約（seed側のみ、登録時1回生成。F-16）
  parent_id     INTEGER,         -- チャンク分割元の文書ID
  chunk_no      INTEGER,         -- 章・節単位の分割番号
  content_hash  TEXT,            -- 差分検知キー（SHA-256。F-11）
  fetched_at    TEXT
);
-- ※`company`列・`doc_type='product'`は訴求の競合チェック（旧F-20）用だったが、ADR-0019により
--   今回は対応しないため設けない。復活時にADRを切って追加する

-- 企画（社内の商品企画・検討案件。ADR-0039）
CREATE TABLE projects (
  id         INTEGER PRIMARY KEY,
  name       TEXT NOT NULL,       -- 企画名
  brief      TEXT,                -- 企画の狙い（タブ①に入れる企画案の文章と同じ粒度）
  category   TEXT,                -- documents.category と同じ語彙
  status     TEXT NOT NULL,       -- 'ongoing'（進行中）| 'launched'（上市済み）| 'cancelled'（中止）
  started    TEXT,                -- 開始年月
  is_sample  INTEGER NOT NULL DEFAULT 1  -- 架空データの印。1なら画面に「サンプルデータ」と表示（ADR-0022）
);

-- 企画×技術の判断（N:Nの中間テーブル。1行＝1組の企画・技術。F-05・F-08、ADR-0039）
CREATE TABLE project_techs (
  id          INTEGER PRIMARY KEY,
  project_id  INTEGER NOT NULL REFERENCES projects(id),
  seed_id     INTEGER NOT NULL REFERENCES documents(id),
  decision    TEXT NOT NULL,      -- 'adopted'（採用）| 'dropped'（見送り）| 'evaluating'（評価中。保留もここ）
  reason      TEXT,               -- 「安定性の問題で見送り」等、一行で分かる理由（自由記述）
  detail      TEXT,               -- 評価データの要点（条件・数値など）
  decided_at  TEXT,               -- 判断した年月
  UNIQUE (project_id, seed_id)    -- 同じ企画に同じ技術を二重登録しない
);
-- 判断は最新の状態だけを持つ（履歴は持たない）。企画そのものの中止は projects.status で表す
-- **「未評価」は行を持たない。** その技術に project_techs の行が1件も無ければ未評価（どの企画でも
--   検討されていない）。行で持つと評価済みの行と矛盾しうるため、行の不在で表す
-- 「やって駄目だったか」が分かることが時間短縮の本体（提案書§4-2）。未評価も判断材料として画面に明示する
-- 1技術が企画Xでは'adopted'、企画Yでは'dropped'になりうる（これを表すためのN:N）

-- 採用された企画から出た商品・訴求（旧tech_usageの商品部分。F-08、ADR-0031・0039）
CREATE TABLE project_products (
  id          INTEGER PRIMARY KEY,
  project_id  INTEGER NOT NULL REFERENCES projects(id),
  product     TEXT,
  brand       TEXT,
  claim       TEXT,               -- 訴求文言（タブ①折りたたみ「既存の訴求」の出どころ）
  launched    TEXT,
  source_url  TEXT
);
-- 1企画＝1商品を前提とする。技術の採用実績は「project_techs.decision='adopted'の企画の商品」として引く
-- PoCではprojects・project_techs・project_productsとも架空データを手で登録し、「サンプルデータ」と明示する
-- 接続ごとに PRAGMA foreign_keys = ON を実行する（SQLiteは既定で REFERENCES を検査しないため）。
--   存在しない技術IDの登録と、判断の記録が残る技術の削除がエラーで止まる。ON DELETE CASCADE は付けない

-- 権利状況（F-19）
CREATE TABLE patents (
  id         INTEGER PRIMARY KEY,
  seed_id    INTEGER NOT NULL REFERENCES documents(id),  -- ADR-0046
  state      TEXT,      -- 'registered' | 'pending' | 'none'
  number     TEXT,
  filed      TEXT,
  registered TEXT,
  expires    TEXT,
  note       TEXT        -- 請求範囲の限定など人が確認すべき事項
);
-- state は一覧段階から表示する。請求範囲の判断は行わず、note に確認事項を書くに留める（ADR-0012）

-- 全文検索（FTS5、BM25内蔵）
CREATE VIRTUAL TABLE documents_fts USING fts5(
  title, body, problem, background,  -- 4項目すべてを索引する（ADR-0027）
  content='',            -- contentless。分かち書き済みテキストをbuild_db側で明示投入
  tokenize='unicode61'   -- Janomeで分かち書き。trigramは不採用（ADR-0011）
);
-- contentless構成なので`documents`へINSERTしただけでは索引は空のまま。`build_db.py`が
-- Janomeで分かち書きしたテキストを明示的に入れる（忘れると「DBには入っているのに検索に
-- 出てこない」不具合になる）。トリガによる自動同期は使わない（ADR-0027）
-- ※BM25は`title`を索引するが、ベクトルは`title`を埋め込まない。対象が違うのは意図的で、
--   短いタイトルはベクトルだと類似度が一様に高く出て最大値方式を壊すため（ADR-0021の実測）

-- ベクトル
CREATE TABLE embeddings (
  doc_id INTEGER NOT NULL REFERENCES documents(id),
  field  TEXT NOT NULL,   -- 'body'（要約）| 'problem'（課題）| 'background'（背景技術）の3つ
  vec    BLOB NOT NULL,   -- float32配列をnumpy.tobytes()で格納。normalize_embeddings=True（ADR-0004・0005）
  PRIMARY KEY (doc_id, field)
);
-- 1文書につきフィールドごとに別ベクトルを持つ（ADR-0021）。検索時は最も類似度の高いフィールドの
-- スコアをその文書のスコアとして採用し、doc_id単位に集約する。
-- 連結して1ベクトルにしないのは、e5の512トークン上限で末尾が切り捨てられるのを避けるため。
-- **`title`は埋め込まない。** 短い文字列はe5では類似度が一様に高く出て順位も不安定で、最大値を
-- 採る方式では常にタイトルが勝ち「ニーズ文→課題」の経路が潰れる（実測で正解が1位→3位に低下）。

-- 検索ログ
CREATE TABLE search_logs (
  id               INTEGER PRIMARY KEY,
  ts               TEXT,
  query            TEXT,
  mode             TEXT,     -- 'cross' | 'normal'
  user_dept        TEXT,     -- 'MK'固定。利用者はマーケ1種類のみ（ADR-0030）。本番で部門が増えたとき使う
  hit_count        INTEGER,  -- 反対側のヒット数。0なら「社内に知見がない空白領域」（ADR-0008）
  top_score        REAL,     -- そのときの最高類似度。タブ②「まだ社内に無い技術」で表示する
  clicked_doc_id   INTEGER,
  clicked_doc_type TEXT
);
```

**データソースの方針（ADR-0012）**
- シーズ側：INPIT開放特許情報データベースで化粧品関連の候補特許を検索・特定し、デモに必要な件数
  （数十件規模）だけ公式な特許公報（J-PlatPat）から人力で転記する。`source='patent_manual'`とし、
  INPIT側の技術概要等の文章はそのまま複製しない。転記する項目は以下のとおり（明細書全文は転記
  しない。原文参照は`url`のリンク先に委ねる）：
  - `documents`：`title`←発明の名称／`body`←【要約】の全文／`background`←【背景技術】／
    `problem`←**【発明が解決しようとする課題】**（ニーズとの照合に最も効くフィールド。ADR-0021）／
    `url`←当該ページURL／`pub_date`←公開日／`category`←自分で判断（ヘアスタイリング等）
  - 【発明の詳細な説明】の全文は転記しない。原文参照は`url`のリンク先に委ねる
  - `patents`：`state`←経過情報から判定／`number`←特許番号または出願番号／`filed`←出願日／
    `registered`←登録日（あれば）／`expires`←存続期間満了日（あれば）／`note`←任意
  - `projects`（企画）・`project_techs`（企画×技術の判断）・`project_products`（商品・訴求）は特許本体とは
    別に、デモ用の架空データとして手で作文し、画面に「サンプルデータ」と明示する（ADR-0022・0039）。
    **同じ技術が企画Xでは採用、企画Yでは見送りになっている例を最低1つ入れる**（N:Nにした意味をデモで示すため）
- ニーズ側：基本はダミーデータを手動登録（`source='dummy'`）。デモで使う検索語1文だけは実在する
  FAQから引用し、出典URLを残す（`source='faq'`）
- 訴求の競合チェック（旧F-20）は今回のPoCでは対応しない（ADR-0019）。他社商品ページの収集は行わない
- 「サンプルデータ」の表示は、架空データが出る場所ごとに付ける（ADR-0043）。表示箇所は次の2か所に
  限定し、`projects.is_sample=1` の行にのみ出す（`is_sample=0` の行には出さない）
  - タブ②詳細の企画一覧
  - タブ①折りたたみの「既存の訴求」

**保存先の方針**：PoCは`documents`/`embeddings`/`search_logs`ともSQLite。`.db`はGit管理外で、
起動時に`schema.sql`＋`fixtures/seeds.sql`から自動組み立てる（ADR-0015・0025）。
**手入力データの編集先は`knowledge.db`本体**で、コミット前に`tools/export_seeds.py`を1回実行して
`seeds.sql`へ書き出す（ADR-0025）。書き出しは`documents.id`を明示し、再構築で技術の番号が変わらないようにする
（`project_techs`が番号で技術を指すため。ADR-0039）。Streamlit Community Cloud
はアプリ再起動でファイルがリポジトリの状態に戻るため、**`search_logs`はアプリ起動中のみ有効**（発表
当日のライブデモは問題なく成立するが、恒久的な集計は本番でSupabase移行後に対応）。

## エラー時の挙動

| 状況 | 挙動 |
| --- | --- |
| 検索クエリが空 | 検索ボタンを無効化する、または「クエリを入力してください」と表示 |
| ヒットなし（反対側でBM25が0件かつベクトル類似度が基準値未満。ADR-0008） | **空白画面にはしない。** 固定の案内文を表示し、関連度%の低い候補カード（ベクトル検索の上位N件）は折りたたみに入れて示す。「似た悩み・既存の訴求」は出さない（ADR-0052。言い換え候補は次フェーズ。ADR-0045）。裏側では`hit_count=0`で記録し、タブ②「まだ社内に無い技術」に個別の1件として追加 |
| 一言要約（`summary_plain`）が生成されていない | 要約欄を非表示にし、原文のみ表示する（固定文へのフォールバックはしない） |
| `patents`/`project_techs`/`project_products`に該当データがない | 「登録なし」「実績なし」「未評価」と明示し、空欄のまま隠さない（データがないことも判断材料になる） |
| FTS5索引と`documents`の内容が不整合 | contentless構成のため自動同期はされない。`build_db.py`がDB構築時に索引を張り直す。整合チェックをテストで確認（ADR-0027） |
| Streamlit再起動で`search_logs`が消える | デモ当日はアプリ起動中のみ有効という前提を手順書に明記。恒久集計は対象外（N-04） |
| 埋め込みモデルへの入力が空文字・極端に長い | 512トークンを超える場合はチャンク分割済み文書として処理。空文字は検索実行前にUIで防ぐ |
