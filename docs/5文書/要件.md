# 要件 — 知の越境検索（PROJECT ZERO / W6）

前提: 今回はStreamlitでWebアプリのPoCを作成する（本番展開は対象外）。

## 機能要件

| ID | 要件 | 顧客価値 | 優先度 | 受入基準（どうなれば満たしたか） |
| --- | --- | --- | --- | --- |
| F-01 | `doc_type`（seed/need）付きスキーマにデータを投入する | 検索対象データが無いと何も実現しない、全機能の土台 | Must | デモに必要な件数のシーズ（要約・背景技術・課題を含む）とニーズが`documents`に格納され、`embeddings`にフィールドごとのベクトルが生成されている（ADR-0021） |
| F-02 | ニーズ⇔シーズのクロス検索（ハイブリッド検索）ができる | 目玉機能。語彙の壁を越えて技術を見つけられる＝差し戻し防止の核心 | Must | ニーズ文を入れるとシーズが、シーズ文を入れるとニーズが返る（双方向のロジック自体は残す。タブ①は'need'固定で使い、シーズ→ニーズはタブ②詳細が使う。ADR-0028）。BM25とベクトル検索をRRF（k=60）で統合している |
| F-03 | 検索結果を関連度順の統一カードリストとして表示する（タブ①検索） | 企画案をそのまま入力するだけで、関連する社内技術が一覧で返る | Must | 企画案の文章を入力すると、関連度・**この技術が解決しようとしている課題**・一言要約・一致理由・権利状況・使用実績を含むカードが関連度順に並ぶ（ADR-0017・0021） |
| F-04 | 検索ログを記録する | 効果測定・ROI（ADR-0001）の根拠データになる | Must | `search_logs`に検索クエリ・所属部署（R&D/マーケ）・反対側のヒット件数が記録される |
| F-05 | 検索結果からエビデンス（原文・評価データ・見送り記録・未評価領域）をワンクリックで参照できる | 「納得できる根拠」を渡す。AIが判定しない方針を実務で支える | Must | 検索結果カードから原文（URL）へ1クリックで遷移でき、詳細画面に`evaluations`の評価済み／見送り／未評価が表示される（ADR-0022） |
| F-06 | 検索方式を切り替えられる（キーワードのみ／意味のみ／両方併用） | デモの核心（0件→N件）を目の前で示せる | Must | 3つの方式をボタン等で切り替えると、結果件数・内容が変わる。短文では0件→N件、長文では順位が入れ替わる（ADR-0026） |
| F-07 | 所属部署（R&D／マーケ）を選び、検索ログに記録する | 部門別のログ集計を可能にし、誰がどこを探しているかを残す | Must | ボタンでR&D/マーケを選択すると`search_logs.user_dept`に反映される。**検索方向は切り替えない**（タブ①はニーズ→技術の片方向に固定。ADR-0009・0028） |
| F-16 | シーズ側の技術文書に「平たく言うと」の一言要約を併記する | 語彙が違うマーケ担当者でも技術文書の意味が分かる | Must | 技術文書の検索結果に一言要約が併記され、原文と「※AIによる要約です。詳細は原文でご確認ください」の注記が表示される。要約は登録時（インデックス時）に1回だけ生成しDBに保存し、検索の都度AIを呼ばない（ADR-0005と非衝突） |
| F-08 | 技術トレース（採用実績・転用実績）を表示する | 差別化できるかどうかを記憶でなく記録で判断できる | Should | 技術データベースの詳細画面で、過去の使われ方（`tech_usage`の実績）が一覧表示される。あわせて**似た課題を解く技術と、その実績・評価（評価済み／見送り／未評価）**が表示される（ADR-0007の実現手段＝同じ側検索＋`tech_usage`・`evaluations`。ADR-0029） |
| F-10 | 検索方式ごとの結果比較トグルを表示する | ハイブリッド検索の効果を発表で可視化して語れる | Should | 同一クエリに対するBM25単独／ベクトル単独／ハイブリッドの結果を並べて比較できる（デモ専用の控えめな帯に配置） |
| F-11 | クローラーが差分検知し、定期的に再実行される | 現場に「登録してください」と頼まず運用ゼロを実現する | Should | 同一URLの再クロール時、内容に変更がなければ再取得・再登録されない（ハッシュ値比較） |
| F-12 | ローカルフォルダ巡回版クローラー（ダミーのWord/PDF取り込み）でデモできる | 社内文書の取り込みを実演で見せられる | Should | 指定フォルダにダミー文書を置くと、クロール処理が内容を読み込みDBに登録する |
| F-13 | 新着シーズと既存ニーズのマッチを検知し通知する | 眠っている技術の出口を継続的に発掘する（展開構想の先取り） | Could | 新規投入した文書が既存の反対側文書と閾値以上の類似度を持つ場合に一覧へ表示される |
| F-14 | マッチ度スコアの根拠を表示する | 関連度の説明可能性を高め、AI非判定方針の裏付けにする | Could | 関連度（%表示）の算出元（BM25/ベクトルどちらでヒットしたか）が表示される |
| F-15 | 検索結果セット全体をRAGで動的に要約する | （見送り方向のため該当なし） | Could | 今回は見送り方向（ADR-0016で検討し不採用。ADR-0005の「検索の都度AIを呼ばない」方針と衝突するため）。F-16の一言要約とは別物 |
| F-17 | 技術データベースタブ（一覧・絞り込み・詳細画面）を提供する | 検索と技術資産の閲覧が1本につながり、資産の厚みを見せられる | Must | タブ②に技術一覧があり、「未使用の技術」「特許 登録済／出願中」「まだ社内に無い技術」で絞り込める。1件開くと詳細（エビデンス・使われ方・似た課題を解く技術とその記録）に遷移する（ADR-0017・0029） |
| F-18 | 一致理由を語句単位でハイライト表示する | 語彙が違う人でも「どこが繋がっているか」が分かる | Should | 検索クエリと技術文書の中で意味的に対応した語句がハイライトされる（例：「べたつく」⇔「可塑化」）。語句ベクトルは事前保存せず検索結果上位に対して都度計算する（ADR-0018） |
| F-19 | 技術ごとの権利状況（特許ステータス）を表示する | 差別化が権利で裏打ちされているかを判断材料にできる | Should | 検索結果一覧の段階で「登録済／出願中／未出願」を示し、詳細画面で出願番号・出願日・登録日・存続期間満了日を表示する（`patents`テーブル、ADR-0012） |
| F-21 | ゼロ件／低ヒット時に言い換え候補を提示する | 検索をゼロ件で終わらせず、次の一手を示せる | Could | ヒット件数が少ない、または0件のとき「もしかして：〇〇 も検索しますか？」を提示する |

## 非機能要件

| ID | 要件 | 受入基準 |
| --- | --- | --- |
| N-01 | 検索応答は数秒以内に返る（生成AIを検索の都度呼ばない） | 意味検索・ハイブリッド検索の応答が体感で待たされない（目安：数秒以内）。要約はインデックス時に1回だけ生成し保存済み |
| N-02 | 検索・埋め込み処理でAPI課金を発生させない | ベクトル化はローカル実行（sentence-transformers）。API課金が発生するのは要約生成のみ |
| N-03 | ログイン機能なしでStreamlit Community Cloudにデプロイできる | 認証なしでURLアクセスするとアプリが起動し、所属部署ボタンが機能する（ADR-0009・0028） |
| N-04 | データの再現性を確保する | `.db`はGit管理外。`schema.sql`と`fixtures/seeds.sql`から初期状態を再現できる。手入力データは`knowledge.db`で編集し、コミット前に`seeds.sql`へ書き出す（ADR-0015・0025） |
| N-05 | 収集データの規約を順守する | シーズ側はINPIT開放特許DBを候補探しのみに使い、その技術概要等の文章は複製しない／実際のシーズ文書は特許公報から少数を人力で転記（自動収集はしない）／robots.txtを守る／EC・口コミサイトは収集対象に含めない（ADR-0012） |
| N-06 | 日本語検索でキーワード検索の「0件」が意図通り再現される | デモ用ニーズ文（**短文**。長文の企画案は対象外。ADR-0026）でキーワード検索（BM25）が0件になることをテストで確認済み（ADR-0011） |

## やらないこと
- 多言語対応（将来の展開構想としてのみ言及）
- 認証・権限管理（所属部署ボタンで代替。ADR-0009・0028）
- 独立したダッシュボード画面（部門またぎ検索率・検索回数推移）**＝旧F-09**。`search_logs`への記録は続け、ゼロ件クエリの可視化はタブ②の絞り込み「まだ社内に無い技術」で代替する（ADR-0017でWon'tへ。ADR-0001の影響欄にある「F-09はShouldのまま」は、より新しいADR-0017が上書き済み）
- J-STAGE APIの利用、企業研究開発ページ・OpenAlexからのシーズ収集（ADR-0012で不採用）
- J-PlatPat・INPIT開放特許DBの自動収集（ロボットアクセス）。特許公報からの人力での少数転記のみ行う（ADR-0012）
- AIによる実現可能性・可否の判定（検索は関連資料の提示に留め、判断は人間が行う）
- ECサイト・口コミサイト（@cosme、Amazonレビュー等）からの自動収集
- 部署名（担当者個人ではなく）以上の粒度でのユーザー識別・権限分岐
- 検索結果のヒット理由の文単位抜粋表示・担当部署表示（ADR-0013。一言要約[F-16/ADR-0016]で代替）
- 企画書作成・実験計画・シミュレーション・過去検討からの論点出しの自動化（ADR-0014。将来の展開構想として言及のみ）
- 訴求の競合チェック・差別化の空き地判定（旧F-20）。他社商品ページの収集経路が未整備なため今回は見送り（ADR-0019。本番フェーズの拡張案として展開構想に記録）

## 実装時に確定するパラメータ（方針は決定済み）
- 「ヒットなし」判定の基準値：暫定0.80で開始し、デモ用データで「ヒットあり／なし」が正しく判定される
  水準に調整する（ADR-0008）
- 関連度スコアの変換式：意味検索側のコサイン類似度を、実データを見てパーセンテージ表示にマッピングする
  （ADR-0010）
- 埋め込みモデルの最終選定：`intfloat/multilingual-e5-small` を第一候補として実装を進め、時間があれば
  `cl-nagoya/ruri-small` と実データで比較のうえ選定する（ADR-0005）
- シーズ側デモ文書の選定：INPIT開放特許情報データベースで化粧品関連キーワードを検索し候補特許を洗い出し、
  デモに必要な件数（数十件規模）だけJ-PlatPatの公式特許公報から人力で転記する（発明の名称・要約・
  背景技術・課題の4項目。明細書全文は転記しない）。INPIT側の技術概要等の文章はそのまま複製しない
  （ADR-0012・0021）
- デモ用クエリの選定：データ投入後に`check_gap.py`を流し、**短文（BM25が0件）と長文（キーワード
  だけでは正解が1位に来ない）の2本**を実測で確定させる。長文は製品カテゴリ名が特許の背景技術と
  一致するため0件にはならない。これを0件にするためにBM25の索引を絞ることはしない（ADR-0026）
